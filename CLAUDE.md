# Win.apk: a guide for contributors and AI assistants

Win.apk runs Android apps on Windows x64 as normal Windows programs: Java on
HotSpot, x86_64 `.so` files loaded by our own ELF loader over a Bionic shim,
graphics by AOSP 14's own HWUI and Skia on ANGLE (D3D11). Started as a port of
Mac.apk; its `runtime/` comes from there. This file is the map of the
repository; open `docs/ARCHITECTURE.md` (how the layers work, an install and a
run step by step), `docs/USER_GUIDE.md` (what the user sees and every setting),
`windows/README.md` (build, tests, env vars, the list of `runtime/` changes) or
`windows/PORTING.md` (design decisions, findings and the milestone plan, ~1100
lines: grep it, don't read it whole) only when a task needs them. The docs must
match the code: a change to a flag, a file name, a setting or what works is
also a change to the document that names it.

**Language.** The maintainer reads Hebrew: replies to the maintainer (and the
short descriptions of commands shown to them) are in Hebrew. Code, comments,
commits and repository documents are in English; user-facing documents have
Hebrew versions under `docs/he/` and `README.he.md`.

**The project's rules.**
- Behave like Android. Layers move onto AOSP's own code (AOSP 14: app, views,
  resources, graphics), not hand-tuned layout or text metrics; where Win.apk
  has to answer itself, it answers as a phone would. Before changing how
  something behaves, ask what Android does in that case and do the same; no
  Win.apk-only rule (a latch, a time window, a heuristic) where Android has a
  plain one: a Google `addAccount` opens its window each time unless one is
  open, as a device's add-account screen does. Where Win.apk cannot do what
  Android does, say how it differs.
- No switches. The runtime has one behaviour: no opt-in or kill-switch
  environment variables or properties. What the environment still carries is
  plumbing, a test hook or a log (`windows/README.md`, "Environment
  variables").
- No app-specific hacks: fix the framework, the shim or the host.

## The launcher (`windows/launcher/launcher_main.cpp`)

Sections in order: paths, settings (registry), Windows integration (file types,
shortcuts), library, running/installing (`start_runtime` gives a child only the
handles it lists; threads post `kInstalled`, `kInstallStarted`, `kRunReady`,
`kRunExited`), HTTP (WinHTTP's `http_get`, a `.part` file kept only whole; `sha256_of`; the `Json` reader), software updates (GitHub's
releases list, the newest non-draft release by version number (pre-releases only while there is no full
release), its `Win.apk-Setup.exe` run only at the release's size, SHA-256, ProductVersion and signer, `updates.h`
`judge_setup`; threads posting `kUpdate*`), theme + drawing helpers, state,
layout, painting (the InfoBar replaces a status bar; `info()` may carry one link, e.g. "What's new"), dialogs, actions (install
with Cancel, launch, Remove with "also remove accounts and data saved by the app"), pages
(Settings, App details, the Google services setup (`show_gms_setup`: Download fetches the three Google apps with apkeep from APKPure (`setup_fetch`) at the versions `google_apps.h` pins (`kGooglePins`: the first install only, then the Play Store updates them; CI's "Google's pinned apps" step downloads and checks each when the pins or apkeep change), one at a time, its button disabled until it ends (`Row::disabled`), APKMirror in the browser when that fails, watches Downloads, installs only Google-signed copies; Google Play in the pane leads there or opens the Play Store): `Row`/`Section`/`Page`, drawn in
the content layer by `paint_page`, `open_page`; Settings > Updates is
`update_sections`, with the check's state in `g_update`, an `UpdateTracker` (`updates.h`)), apps in the window (the Store and Google Play: `Embedded` `g_store_app` and `g_play`, a panel each, `WINAPK_EMBED_PARENT`, `show_embedded`; the Store's app, `app.apkstore`, a system component like Google's three apps: got from israel2176/win.apk-store's latest release at the first opening, updated with the daily check, kept only at GitHub's size and SHA-256, installed quietly, threads posting `kStoreApp*`, `g_store_setup` a `StoreSetup`; `appops::grant_builtin_store` allows its "Install unknown apps" at its first install), install window, log window
(RichEdit), the Threads window (debug mode: `show_debugger`, a ListView over `g_dv`; `debug_thread` looks once a second at every runtime's process tree and threads and asks each debug agent, posting `kDebugSnapshot`), launch splash, drag and drop (`IDropTarget`), main `wnd_proc`, the
installed-apps registry, the install helper (`install`/`uninstall` verbs),
permissions (`namespace appops`: the signed app-ops store and the
`runtime-permission`, `special-access`, `app-details` questions the runtime asks
through, upstream's macapk-installhelper verbs, drawn by `run_prompt`, for every
dangerous group: `kGroupRows` must match
`runtime/java/com/macapk/loader/RuntimePermissionGroups.java`; the details
page's Permissions rows, which stop a running app on revoke), single instance
(`forward_to_running`, `maybe_quit`), `wWinMain`.

- One process serves the library, the install window and the splashes. A
  second `Win.apk.exe` hands its files (or "show the library") to the first
  in a `WM_COPYDATA` and exits; Explorer's one-process-per-file starts meet on
  the `Local\WinApk-launcher` mutex. The library window always exists but is
  shown only when asked for: an APK from Explorer shows only the install
  window, `--run` only the app's starting window. The hidden process quits when nothing is
  left (`maybe_quit`).
- Launching: `launch()` shows the starting window at once (`show_splash`: a
  normal window with the app's name, icon and AppUserModelID, of the size the
  app's window opens at, `app_window_size` over `host/window_fit.h`, the
  runtime's own arithmetic); `run_thread` passes it as `WINAPK_START_WINDOW`,
  so the runtime opens the app's window over it, and `WINAPK_READY_EVENT`,
  and waits on that or the process. Ready brings the app's window forward and
  closes the starting window; an exit with an error first turns it into the error with
  Show log, a clean one (exit code 0) closes it, as a phone does. The run's state is
  `g_runs` (`app_runs.h`), changed only through `begin_run`, `stop_run`,
  `expect_run_end`, `finish_run` and `run_thread`; what its end says is
  `RunEnd::kind()`. Installs likewise: `g_installs` (`installs.h`), through
  `begin_install`, `cancel_install`, `finish_install`, `install_thread` and
  `install_into_library`; `g_jobs` is only the install window's record of the
  batch.
- One home per action: the tile's menu is Open, Stop, App details, Remove;
  everything else per app is on the App details page, its log too (Show log,
  in the log window; Ctrl+L opens the newest); Settings > Troubleshooting >
  Logs opens the logs folder, and with Debug mode on has Threads (every running app; an app's own
  is on its details page, Ctrl+T opens it on all); the failure states of the install window and the
  splash have Show log, and Report a problem as a link under their sentence
  (`report_problem`: asks in a `Prompt`, then the issue form prefilled by URL
  and the log selected in Explorer; nothing uploaded), which the details page
  has too. An app that crashed gets Android's crash dialog (`show_crash_dialog`, for a run
  whose exit code `include/winapk/app_exit.h` counts as a crash: App info, Close app, Show log
  and Report a problem as links), one not taking input for five seconds Android's "isn't responding"
  (`ask_not_responding`: over the starting window, or asked by the runtime through the
  `app-not-responding` verb). Don't add a second way to an action.
- Menus are the launcher's own (`run_menu`, `PopupMenu`: themed, a glyph per
  item, an app header), not `TrackPopupMenu`; only the log picker still uses
  the system menu.
- Dialogs are the launcher's own too (`Prompt`, in the dialogs section:
  `run_dialog` for its questions, modal to the window asking; `run_prompt`
  for an app's, over the app's window), not TaskDialog or MessageBox: the
  accent button first, Enter on Cancel for anything destructive, Esc no answer.
- Points from screen coordinates (WM_NCHITTEST's) go through `client_point`:
  in a mirrored window ScreenToClient already mirrors x, as mouse messages do.
- An install's library name (`install_name`) is the package when the file
  name starts with one (`com.waze_5.26..._apkmirror.com.apkm` -> `com.waze`),
  else the file name up to its version; a package the library has keeps its
  app's name, so the file updates it.
- The version is `launcher.rc`'s VS_VERSION_INFO (`version()`): 0.1.0 unless
  CMake's `WINAPK_VERSION` (the release workflow passes its tag; `ci.yml` the newest
  release tag + `-dev.<run>`, which the update check counts as that release) writes
  `winapk_version.h`. The update check compares it with the newest release's tag.
- Settings > Google account asks `winapk-runtime --gms accounts|signin-window|signout`
  (`run_gms`, stdout captured, stderr in `logs\gms.log`); exit codes 0 done,
  1 error, 2 cancelled. No device registration row: the maintainer does not
  want one in Settings. A page row may carry one text link under its detail (`Row::link`).
- Every user-visible string goes through `tr(L"English")` or
  `fmt(L"... {0} ...", {args})`; add the Hebrew to the table in `tr()`.
- Hebrew = RTL: windows get `WS_EX_LAYOUTRTL`, `buffered_paint` mirrors the
  layout, and `draw_text` / `draw_image` un-mirror text and pictures. Always
  draw text with `draw_text` and images with `draw_image`, never directly.
  Layout and hit-testing code stays left-to-right.
- Icons are glyphs from Segoe Fluent Icons / MDL2 Assets (`kGlyph*`).
- A button that starts something stays disabled until it has ended
  (`Row::disabled` on a page), so a second click cannot start it twice.

## Build and check

- Toolchain: **clang only** (MSVC cannot emit System V calls). CI builds on
  `windows-latest` with MSYS2 CLANG64.
- Quick launcher-only compile check on Linux (no full CMake needed):
  `apt-get install g++-mingw-w64-x86-64-posix`, then
  `x86_64-w64-mingw32-windres windows/launcher/launcher.rc -O coff -o l.res` and
  `x86_64-w64-mingw32-g++-posix -std=c++17 -Wall -Wextra -Wno-missing-field-initializers -DUNICODE -D_UNICODE -D_WIN32_WINNT=0x0A00 -municode -mwindows -static windows/launcher/launcher_main.cpp l.res -o Win.apk.exe -lcomctl32 -lshell32 -lole32 -luuid -lgdiplus -ldwmapi -luxtheme -lgdi32 -lwinhttp -lbcrypt -lcrypt32 -lwintrust -lversion`.
- Looking at the UI: `apt-get install wine64 xvfb xdotool`; Wine is in
  `/usr/lib/wine` (`wine64`). Run under `Xvfb :9`, screenshot with
  `import -window root`. In a cloud container Wine 9 aborts at once
  (`free(): invalid pointer`) while `/run/user/<uid>` is missing: run
  `mkdir -p /run/user/0 && chmod 700 /run/user/0` first. Start Wine (even
  `winepath`) with `DISPLAY` set, or the wineserver it leaves has no display
  and ANGLE then finds no D3D11 renderer ("Could not create DXGI factory").
  Wine lacks Segoe fonts, so icon glyphs show as boxes.
  For the README screenshots (`docs/images/`), stand-in fonts were dropped into
  the prefix's `C:\windows\Fonts`: Open Sans instanced and renamed "Segoe UI" /
  "Segoe UI Semibold" (fontTools), and a "Segoe Fluent Icons" built from
  Fluent UI System Icons SVGs on the same code points (it needs name IDs 3, 4
  and 6 or Wine's GDI+ will not find it). Wine's GDI+ does no bidi, so Hebrew
  screenshots come out wrong: take those on Windows.
- Full build and tests: `windows/README.md`, "Build and run".

## Conventions

- Win.apk code goes in `windows/`. Touch `runtime/` only for a needed Windows
  hook, and add it to the list in `windows/README.md`.
- Match the surrounding style: C++17, 120 columns, comments say why.
- Don't add app-specific hacks; fix the framework, shim or host.
- PRs go to `main`; CI must be green. Releases only via the manual
  `windows-release.yml` run.
- After a push to a PR, once its CI run has finished, give the link to that
  run's `winapk-setup` artifact (the installer) without being asked:
  `https://github.com/<owner>/<repo>/actions/runs/<run>/artifacts/<id>`.
