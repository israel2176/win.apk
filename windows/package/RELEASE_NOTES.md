A pre-release for testing: Win.apk runs Android apps on Windows 10/11 x64 as ordinary Windows programs. It is an unofficial port of Mac.apk.

## Getting started
- **Install:** run `Win.apk-Setup.exe`. It installs per user, with no administrator rights, and puts Win.apk in the Start menu. SmartScreen warns because the build is not signed: **More info**, then **Run anyway**. If you would rather not install, unzip `Win.apk-windows-x64.zip` and start `Win.apk.exe`.
- **Add apps:** double-click `.apk`, `.apkm`, `.xapk` or `.apks` files in Explorer (only a small install window opens: the app's icon and name, one line on what it is doing, the log behind "Show details", and Open / Close / Show in library at the end; several files share one window), drag them onto the library, or get them from the **Store** (F-Droid's free and open-source apps: search, Install, Update). Each app gets its own icon in the library, the Start menu and the desktop.
- **Open apps:** a launch window with the app's icon shows at once and stays until the app's window is up; if the app does not start, it says so in a sentence with **Show log**. Shortcuts use it too.
- **The library:** Library, Store and Settings in the left pane. Right-click an app for its menu (the app's icon and version, Open, Stop, App details, Remove); **App details** holds everything else about one app, its log included. An app's folders are named after its package (`apps\com.waze`), not after the downloaded file. **Remove** can also delete what the app saved. Each action has one place.
- **Updates:** Win.apk checks GitHub for a newer release about once a day (Settings > Updates turns that off, or checks now) and says so in the library, with what changed; **Update** downloads the installer and runs it, keeping your apps and their data.
- **Included:** Java, ANGLE and the clang that translates ARM code. `README.txt` in the package and `docs/USER_GUIDE.md` in the repository have the details.

## What works
- **Java/Kotlin apps:** each opens in its own window, with mouse, wheel and keyboard input. Back is Escape, Alt+Left or the mouse's back button.
- **Resizable windows:** drag an edge, maximize or snap an app's window and the app lays itself out for the new size, as an Android desktop window does. An app that fixed its orientation keeps it, with black bars. Each app remembers its size; its details page resets it.
- **Orientation:** apps open in landscape, the shape of a PC screen, unless the settings say portrait. An app's details page turns just that app the other way. An app whose manifest requires one orientation always opens that way.
- **English and Hebrew:** Setup and the library follow the Windows display language; Hebrew is laid out right to left.
- **OpenGL ES:** from Java (`GLSurfaceView`, libGDX) and from an app's native code (SDL games), on ANGLE (Direct3D 11), falling back to WARP or SwiftShader without a GPU.
- **Games in native code:** `NativeActivity` apps get their window, input queue and configuration as on Android.
- **Native libraries:** apps that ship `lib/x86_64` libraries load them directly. Apps that only ship `lib/arm64-v8a` libraries have their ARM code translated to x64 in the background (`winapk-aot`, compiled with clang for your CPU). The app opens at once on an ARM JIT and switches to the translated code as it becomes ready; large libraries are translated only where the app's code ran. The translation stays out of your way: lowest priority, one core while you use the PC (more only while you are away), none on battery saver or under a full-screen program, never the memory other programs need, and it goes on where it stopped after a restart. It now also finds the code of stripped libraries (most of them), so more of an app runs translated.
- **Sound:** AudioTrack, SoundPool and MediaPlayer audio from Java (WAV, Ogg, MP3, AAC and what Windows decodes), AAudio from native code, and the microphone.
- **Video:** `MediaPlayer` and `VideoView` play MP4, MOV and other files Windows decodes (H.264 and AAC always; HEVC, VP9 and AV1 with Microsoft's codec packs), from a file or an http(s) URL, into the app's `SurfaceView` or `TextureView`, with the sound in step, pause, seeking and looping. ExoPlayer and other `MediaCodec` players decode H.264 video and AAC/MP3 audio on the same Media Foundation decoders.
- **Web content:** WebView and Custom Tabs on WebView2 (Microsoft Edge), including `shouldInterceptRequest` for Cordova and Capacitor apps.
- **Camera and location:** webcams through the Camera, camera2 and CameraX APIs (a virtual camera when there is none); location from Windows' location service, behind Windows' privacy settings.
- **Storage:** files, SharedPreferences and SQLite. Shared storage (Downloads, Pictures, Documents, Music, Movies) is your own Windows folders; a setting turns that off.
- **Permissions:** apps ask for every permission group as on Android, in a small window over the app with its icon and one question (Allow / Don't allow, and no more asking after a second refusal): storage and media, location (precise or approximate, and "all the time" separately), camera, microphone, contacts, calendar, phone, call logs, SMS, notifications, nearby devices, physical activity and body sensors, plus "All files access", "Media management", "Display over other apps" and "Install unknown apps". The answers survive restarts and updates. An app's App info screen (a switch per permission), or its details page in the library, turns each one on or off or resets them; taking a permission away stops the app, as on Android.
- **Wi-Fi:** `WifiManager` reports the PC's Wi-Fi: on or off, the current network (name, BSSID, signal, frequency, link speed, IP), the DHCP configuration (gateway, netmask, DNS) and the scan results, with `startScan` and `SCAN_RESULTS_AVAILABLE` when the scan is done, and the state, connection and signal broadcasts as Windows reports them. Network names and scan results need location access for desktop apps in Windows' privacy settings, the same rule Android applies with the location permission. Apps cannot connect the PC to a network.
- **Bluetooth:** the paired devices (pair them in Windows Settings), serial connections to and from them (`BluetoothSocket` and `BluetoothServerSocket` over RFCOMM, with the SDP record), Bluetooth LE scans (`BluetoothLeScanner`, with filters and the advertisement data) and LE connections (`BluetoothGatt`: services, reading and writing characteristics and descriptors, notifications through the client characteristic configuration, the MTU), behind the Nearby devices permission (and location for scan results, as on Android). Not there: classic discovery and pairing from the app, LE advertising and the GATT server, the audio, HID and other profiles, L2CAP channels, and the RSSI of a connected LE device.
- **Notifications:** what an app posts shows as a Windows notification in the Action Center, with the app's name and icon, its text, large icon and progress bar; a low-importance channel's go there without popping up, and cancel removes them. Clicking one brings the app forward and opens what a tap would on Android, while the app is running.
- **Native crashes:** an app's own crash handler (Breakpad, Crashlytics, Unity's, Mono's and Dart's null checks) gets its signals as on Android; `dlclose` really unloads a library. When native code does crash, the app's log names the library and offset and a minidump is written next to it (`logs\crash-<app>-<date>.dmp`, the last three per app) to attach to an issue.
- **Google sign-in and Play services:** apps that sign in with Google, check a Play licence, use Firebase Analytics or Cloud Messaging, or ask Play services for location get Win.apk's own in-process stand-ins, as on the Mac. Signing in opens Google's own page in a window of its own (it needs the WebView2 Runtime); Win.apk never sees the password. Signing in works behind a filter or proxy whose certificate Windows trusts, such as NetFree, from Settings as from an app. One account serves every app: an app's "Sign in with Google" opens that window at once when none is signed in yet, and a round account button at the end of the library's toolbar shows who is signed in, with the account's profile picture. Settings > Google account adds and removes the account.
- **Desktop services:** clipboard, file pickers and game controllers.

The compatibility sweep (`windows/test/compat/`) boots about 90 open-source apps headless on every pull request; its report is attached to each run.

## Not yet
- Native code for 32-bit ARM only (`armeabi-v7a`).
- Video from an app's native code (the NDK's `AMediaCodec` and `AMediaExtractor`), `MediaExtractor`, and Opus, Vorbis or FLAC audio through `MediaCodec` (an ExoPlayer stream with such audio stays silent).
- OpenSL ES from native code: engines that use it get no sound.
- Vulkan, and real sensor input (the accelerometer and the others report a phone lying still).
- Play Store features: in-app purchases, Play Integrity, the Maps SDK's map.
- Notification action buttons are not shown.

## Reporting
Open an issue on GitHub with the "An app does not work" template. Please include the app's name, version and where it came from, the exact steps to reproduce the problem, a screenshot of the app at the point it goes wrong, and attach the app's log (**Show log** in the launch window, or `%LOCALAPPDATA%\Win.apk\logs\run-<app>.log`; the whole file). `docs/APPS.md` in the repository lists common apps and the problems already known. If Win.apk is useful to you, a star on the repository helps.
